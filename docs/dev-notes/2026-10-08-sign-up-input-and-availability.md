# 회원가입 화면의 입력 검사와 사전 중복 확인

## 문제와 선택

가입 화면에서 형식이 틀린 아이디·닉네임까지 서버에 조회하면 불필요한 요청과 `400` 오류가 발생한다. 사용자는 화면이 먼저 입력 규칙을 검사하고, 규칙에 맞는 값만 API로 보내는 방식을 선택했다. 서버의 검증은 직접 API를 호출하는 요청에도 적용되므로 유지한다.

화면은 다섯 필드를 API 계약과 같은 규칙으로 검사한다. 아이디·닉네임은 유효한 값에서만 약 500ms 입력이 멈춘 뒤 `GET /api/members/availability`를 호출한다. 입력칸을 떠나면 즉시 확인하고, 한글 조합 중에는 조회하지 않는다. 값이 바뀌면 이전 표시를 숨기고 진행 중인 요청을 취소하며, 취소에 응답하지 않는 오래된 결과도 무시한다.

## 고려한 방식

- 서버 검사만 사용하면 화면 규칙의 중복 구현은 줄지만, 형식 오류마다 요청과 왕복 시간이 발생한다.
- 화면 검사만 사용하면 직접 API 요청을 통제할 수 없고, 조회 이후 다른 회원이 같은 값을 먼저 등록하는 상황도 막지 못한다.

사전 조회는 입력 시점의 안내다. 최종 가입의 DB 고유성 검사와 `409` 응답을 대신하지 않는다.

## 확인한 결과와 남은 작업

- 화면 테스트에서 형식 오류 표시, 유효한 값만 500ms 후 조회, 한글 조합 중 조회 보류, blur 즉시 조회, 오래된 응답 무시를 확인했다. 프런트엔드 테스트 9개와 lint·build가 통과했다.
- 로컬 Spring 서버와 Vite `/api` proxy를 실행해 `GET /api/members/availability?field=loginId&value=rental1`이 `200 {"available":true}`로 전달되는 것을 확인했다. 이 값은 확인 당시 로컬 DB의 상태다.
- 가입 `POST` 연결과 최종 `400`·`409` 표시, 실제 화면에서의 전체 가입 흐름은 다음 단계에서 확인한다.
