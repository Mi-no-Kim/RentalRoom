# 세션 로그인 요청의 CSRF 토큰을 조회 API와 헤더로 전달하기

- **상태:** w1 계약 작성·자체 검토 완료, 구현 전
- **발견일:** 2026-10-08
- **관련 기능:** Issue #4 w1 로그인·로그아웃 계약

## 배경

- RentalRoom은 브라우저 쿠키로 세션 ID를 보내는 로그인 방식을 선택했다. 브라우저가 쿠키를 자동 전송하는 요청에서는 상태 변경을 사용자가 의도했는지 확인할 CSRF 방어가 필요하다.
- 프런트엔드는 React에서 JSON API를 호출한다. 기존 회원가입 `POST /api/members`는 현재 CSRF 검사 제외 경로이며, 로그인·로그아웃 API는 아직 없다.

## 관찰

- Spring Security는 JavaScript 화면이 CSRF 토큰을 요청 헤더로 보내는 방식과, 토큰을 별도 조회 API 또는 JavaScript가 읽을 수 있는 쿠키로 제공하는 방식을 설명한다. 로그인 성공·로그아웃 성공 후 이전 토큰이 지워질 수 있어 다시 받아야 한다. [Spring Security CSRF 문서](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)
- 현재 구현에는 CSRF 조회 API와 로그인·로그아웃 요청이 없으므로 선택한 흐름의 실행 결과는 없다.

## 고민한 선택지

1. **공개 조회 API + 헤더:** 화면이 `GET /api/auth/csrf`에서 토큰을 명시적으로 받고, 상태 변경 요청에 `X-CSRF-TOKEN` 헤더로 보낸다. 화면 시작과 로그인·로그아웃 성공 후 언제 새 토큰이 필요한지 드러난다. 별도 조회 요청과 API 계약이 필요하다.
2. **읽을 수 있는 CSRF 쿠키 + 헤더:** 화면이 별도 CSRF 쿠키의 값을 읽어 요청 헤더에 복사한다. 조회 API를 줄일 수 있지만 SPA에서 토큰 생성·갱신과 쿠키·헤더 처리를 맞춰야 한다. 인증용 세션 쿠키와 CSRF 쿠키의 역할도 구분해야 한다.

## 결정과 수정

- 사용자는 첫 번째 방식을 선택했다. `GET /api/auth/csrf`는 로그인 전에도 호출할 수 있어야 하므로 공개 경로로 둔다. 화면은 받은 토큰을 로그인·로그아웃을 포함한 CSRF 보호 대상 변경 요청의 `X-CSRF-TOKEN` 헤더에 넣는다.
- 로그인 성공과 로그아웃 성공 후에는 다음 변경 요청 전에 새 CSRF 토큰을 조회한다. `{"token":"..."}` 응답, 화면 메모리 보관, 토큰 실패 `403 INVALID_CSRF_TOKEN`은 [회원 로그인 API 계약](../api/member-login.md)에 정했다.
- 세션 만료 후 이전 토큰으로 보낸 변경 요청은 인증 오류보다 CSRF `403`이 먼저 날 수 있다. 화면은 `/me`로 인증 상태를 확인하고 새 토큰을 조회해야 한다.
- 사용자가 계약 작성을 맡긴 뒤 API 계약 문서를 작성했다. 제품 코드는 변경하지 않았다.

## 검증

- 현재 `SecurityConfig`에서 CSRF 제외로 지정한 것은 `/api/members`다. 새 조회 API나 로그인·로그아웃 경로는 아직 없다.
- [Spring Security CSRF 지침](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)에서 공개 조회 API와 헤더 전달, 로그인·로그아웃 뒤 새 토큰 조회, 세션 만료 뒤 토큰 검증 실패 가능성을 확인했다. 직접 만든 로그인은 이전 토큰 폐기를 인증 절차에 연결해야 하며, 보안 필터의 CSRF 오류를 계약한 JSON으로 바꾸는 처리도 별도로 필요하다. 현재 코드에서 이를 실행 검증한 결과는 없다.
- 구현 후 토큰 없는 로그인·로그아웃의 거부, 유효한 토큰의 수락, 로그인·로그아웃 후 새 토큰 조회와 후속 변경 요청을 확인해야 한다. 기존 회원가입의 공개 동작도 회귀 확인한다.

## 남은 내용

- 백엔드의 토큰 저장·갱신 처리와 SPA 요청 흐름을 구현 시 사용자 주도로 정하고, 실제 브라우저와 통합 테스트에서 확인한다.
