# 회원 로그인 상태를 서버 세션으로 관리하기로 선택

- **상태:** w1 계약 작성·자체 검토 완료, 구현 전
- **발견일:** 2026-10-08
- **관련 기능:** Issue #4 w1 회원 로그인 계약

## 배경

- 회원가입으로 만든 자체 아이디·비밀번호를 사용해 로그인하고, 이후 예약 요청에서 회원을 식별해야 한다.
- 현재 `SecurityConfig`는 가입 `POST`와 가입 전 중복 확인 `GET`만 공개하고 나머지 요청에 인증을 요구한다. 로그인과 인증 상태 복원은 아직 구현되지 않았다.

## 관찰

- 사용자는 쿠키·세션·JWT의 관계와 쿠키 자동 전송에 따른 CSRF 문제를 학습한 뒤, RentalRoom에서는 세션 방식을 선택하고 다른 프로젝트에서는 다른 방식을 시도하기로 했다.
- 이어서 새로고침 후 로그인 유지, 30분 무활동 만료, 로그아웃 시 서버 세션 즉시 무효화, 자동 로그인 제외라는 기본안을 선택했다.
- 이 선택은 구현·테스트 결과가 아니라 Issue #4의 인증 방식 결정이다. 처리량이나 보안 우위를 검증한 결과로 해석하지 않는다.

## 고민한 선택지

1. **서버 세션:** 브라우저의 쿠키는 세션 ID를 전달하고, 서버가 로그인 상태를 보관한다. 서버에서 세션을 무효화해 로그아웃을 처리할 수 있다. 세션 저장·만료와 쿠키 자동 전송에 따른 CSRF 보호를 설계해야 한다.
2. **인증 정보 쿠키:** 서명·암호화한 인증 정보를 쿠키에 담아 서버가 검증할 수 있다. 별도 세션 조회 없이 인증할 수 있지만, 발급된 쿠키의 갱신·강제 무효화를 따로 설계해야 한다.
3. **Bearer JWT:** 클라이언트가 토큰을 `Authorization` 헤더로 보낼 수 있다. 서버 세션 없이 서명과 만료를 검증할 수 있지만, 토큰 보관·갱신·로그아웃 시 무효화 방식을 정해야 한다. JWT를 쿠키로 보내면 쿠키 자동 전송에 따른 CSRF 검토도 다시 필요하다.

## 결정과 수정

- 사용자가 RentalRoom의 인증 방식으로 서버 세션을 선택했다. 다른 프로젝트에서는 다른 방식을 경험하려는 의도를 밝혔다. 이 밖의 선택 이유는 아직 확인되지 않았다.
- 세션에는 로그인 상태를 두고 브라우저 쿠키에는 세션 ID를 전달한다. 새로고침 후에도 유효한 세션은 유지하고, 서버가 마지막 요청을 받은 뒤 30분 동안 요청이 없으면 만료시키는 것으로 `무활동`을 해석한다. 로그아웃은 서버 세션을 즉시 무효화하며 자동 로그인 기능은 넣지 않는다.
- 브라우저 종료만으로 서버 세션이 즉시 끝난다고 가정하지 않는다. 세션 쿠키 속성과 성공·실패 응답은 [회원 로그인 API 계약](../api/member-login.md)에 정했다. 구체적인 세션 저장소는 구현·배포 조건을 보고 정한다. CSRF 토큰 전달 선택은 [별도 노트](2026-10-08-session-csrf-token-delivery.md)에 기록했다.
- 사용자가 계약 작성을 맡긴 뒤 API 계약 문서를 작성하고 기존 가입 계약·보안 설정과 대조했다. 제품 코드는 변경하지 않았다.

## 검증

- 현재 `SecurityConfig`에 로그인 경로와 세션 로그인 동작이 없는 것을 확인했다. 세션 선택 자체를 검증하는 실행 결과는 아직 없다.
- 계약을 다시 대조하면서 `MemberRepository.findByLoginId`와 `PasswordEncoder` 사용 사례는 확인했지만, 인증 정보를 요청 사이에 보존할 설정·코드는 아직 없음을 확인했다. 직접 만든 로그인은 인증 상태를 세션에 명시적으로 저장하고 세션 ID를 교체해야 한다는 [Spring Security 세션 관리 지침](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)을 구현 점검 항목에 반영했다.
- 아이디 없음과 비밀번호 불일치에 동일한 `401`·본문을 사용해도 비밀번호 확인을 한쪽에서만 건너뛰면 응답 시간으로 차이가 드러날 수 있다는 [OWASP 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)을 확인했다. 구현 리뷰에서 함께 살핀다.
- Issue #4 w2 구현 후 올바른·잘못된 자격 증명, 새로고침 뒤 회원 식별, 30분 무활동 만료·로그아웃 뒤 인증 거부와 CSRF 실패 경로를 계약에 맞춰 확인해야 한다.

## 남은 내용

- 작성한 계약대로 인증 저장·세션 ID 갱신·30분 무활동 만료·로그아웃 무효화와 응답을 구현 후 검증한다. 현재는 실행 검증 전이다.
- 단일 서버에서 시작할지, 세션 저장소를 어디에 둘지는 실제 실행·배포 조건과 함께 결정한다. 여러 서버의 세션 공유는 현재 검증된 요구가 아니다.
