# 회원가입 API 계약

- **상태:** 회원가입 `POST`와 가입 전 중복 확인 `GET` 구현·통합 테스트 검증 완료, w3 가입 화면 연결·로컬 검증 완료
- **범위:** 회원가입 요청과 가입 전 중복 확인의 입력, 중복 판단, 성공·오류 응답

## 요청

`POST /api/members`에 `Content-Type: application/json`으로 보낸다. 다섯 필드는 모두 필수다.

| 필드         | 의미                   | 입력 규칙                                                                                                                                              |
| ------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `loginId`    | 로그인에 사용할 아이디 | 영문 소문자·숫자 6~20자. 대문자·공백은 오류로 거부하며 자동 변환하지 않는다.                                                                           |
| `password`   | 비밀번호               | 보이는 ASCII 문자 8~32자. 영문 대문자·소문자·숫자·ASCII 기호 네 종류 중 두 종류 이상을 포함한다. 공백·제어 문자·한글 등 다른 유니코드 문자는 거부한다. |
| `familyName` | 성                     | 완성형 한글 음절 `가`~`힣` 1~12자                                                                                                                      |
| `givenName`  | 이름                   | 완성형 한글 음절 `가`~`힣` 1~12자                                                                                                                      |
| `nickname`   | 닉네임                 | 완성형 한글 음절 `가`~`힣`, 영문 대소문자, 숫자, `_`, `-`로 2~12자                                                                                     |

`보이는 ASCII 문자`는 `!`(U+0021)부터 `~`(U+007E)까지다. 이 중 영문자·숫자가 아닌 문자를 비밀번호의 `ASCII 기호` 한 종류로 센다. 길이는 허용된 문자의 개수로 센다. 입력값의 앞뒤 공백도 자동으로 제거하지 않는다.

```http
POST /api/members
Content-Type: application/json

{
  "loginId": "rental1",
  "password": "Example9!",
  "familyName": "김",
  "givenName": "민수",
  "nickname": "Min_1"
}
```

## 중복 기준

- `loginId`와 `nickname`은 각각 고유하다. 성과 이름이 같은 다른 회원은 가입할 수 있다.
- 닉네임의 영문 대소문자 차이는 중복을 구분하지 않는다. 예를 들어 기존 `Min_1`이 있으면 `min_1`은 거부한다.
- 아이디에도 영문 대소문자를 무시하는 중복 원칙을 적용한다. 현재 아이디 입력은 소문자만 허용하므로 대문자가 섞인 값은 중복 검사 전에 입력 오류로 거부한다.
- 최종 가입에서는 데이터베이스의 고유 인덱스가 중복을 막고, 충돌을 해당 필드의 `409`로 응답한다.

## 가입 전 중복 확인

인증 없이 `GET /api/members/availability`로 아이디 또는 닉네임 하나의 현재 사용 가능 여부를 조회한다. `field`는 `loginId` 또는 `nickname`이며, `value`는 확인할 입력값이다. 두 매개변수는 필수다.

```http
GET /api/members/availability?field=loginId&value=rental1
```

입력 형식이 해당 가입 필드의 규칙에 맞으면 `200 OK`와 불리언 `available`을 반환한다. 기존 값과 정확히 같거나 닉네임의 영문 대소문자만 다르면 `false`다. 아이디의 대문자 입력은 자동 변환하지 않고 입력 오류로 처리한다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"available":true}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"available":false}
```

`value`가 비었거나 해당 필드의 입력 규칙에 맞지 않으면 `400 Bad Request`와 기존 오류 형식 `{"code":"INVALID_INPUT","field":"loginId"}` 또는 `field=nickname`을 반환한다. `field`가 누락되거나 지원하지 않는 값이면 `400`과 `{"code":"INVALID_INPUT","field":"field"}`를 반환한다. 조회 결과는 값을 예약하지 않으므로, 조회 이후 가입 요청에서는 여전히 `409`가 발생할 수 있다.

### w3 첫 단계: 서버 구현 기준

이 조회는 회원을 생성하거나 값을 선점하지 않는다. 아래 순서와 결과를 만족하도록 구현한다.

1. `field`가 `loginId`·`nickname` 중 하나인지 확인한다. 누락되거나 다른 값이면 `400 INVALID_INPUT`, `field=field`를 반환한다.
2. `value`를 위 [요청](#요청) 표의 해당 필드 규칙으로 확인한다. 누락·빈 값·형식 오류이면 `400 INVALID_INPUT`과 선택한 필드명을 반환한다. 앞뒤 공백 제거와 대문자 자동 변환은 하지 않는다.
3. 유효한 값만 기존 회원과 비교한다. 아이디는 소문자만 유효하므로 같은 아이디가 있는지 확인한다. 닉네임은 기존 값과 영문 대소문자만 다른 경우도 사용 중으로 판단한다. 결과를 `200 {"available":true|false}`로 반환한다.
4. 인증하지 않은 요청에도 이 `GET` 경로를 허용한다. 가입 `POST`의 공개 범위와 최종 DB 고유성·`409` 처리는 유지한다.

현재 코드에서 확인할 위치는 `MemberController`의 조회 경로와 응답, `MemberService`의 입력 확인·조회 흐름, `MemberRepository`의 존재 여부 조회, `SecurityConfig`의 공개 `GET` 설정이다. 구현 위치와 조회 방식은 선택할 수 있지만, 닉네임 조회 결과는 DB의 대소문자 중복 규칙과 일치해야 한다. `GET`은 읽기 요청이므로 CSRF 제외 경로를 추가할 필요는 없다.

다음 사례를 PostgreSQL을 사용한 통합 테스트에서 인증 없이 확인한다. 기존 회원은 `loginId=rental1`, `nickname=Min_1`로 가정한다.

| 요청의 `field` / `value`     | 기대 결과                             |
| ---------------------------- | ------------------------------------- |
| `loginId` / `rental2`        | `200`, `available=true`               |
| `loginId` / `rental1`        | `200`, `available=false`              |
| `nickname` / `new_1`         | `200`, `available=true`               |
| `nickname` / `min_1`         | `200`, `available=false`              |
| `loginId` / `Rental1`        | `400 INVALID_INPUT`, `field=loginId`  |
| `nickname` / 빈 값 또는 누락 | `400 INVALID_INPUT`, `field=nickname` |
| 누락 또는 미지원 `field`     | `400 INVALID_INPUT`, `field=field`    |

서버 구현 후에는 기존 가입 `POST`의 성공과 중복 `409` 테스트도 함께 실행한다. 사전 조회에서 `available=true`였더라도 그 뒤 다른 요청이 먼저 가입할 수 있으므로, `GET` 결과로 `POST`의 DB 중복 판정을 대체하지 않는다.

## 응답

가입 성공은 `201 Created`이며 본문은 비어 있다. 회원 정보·비밀번호·로그인 상태·인증 정보는 이 응답에 포함하지 않는다.

```http
HTTP/1.1 201 Created
```

입력 규칙 위반이나 필드 누락은 `400 Bad Request`다. 오류 본문은 `code`와 `field`를 가진다.

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"code":"INVALID_INPUT","field":"password"}
```

유효한 입력에서 아이디나 닉네임이 이미 사용 중이면 `409 Conflict`다.

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{"code":"LOGIN_ID_ALREADY_USED","field":"loginId"}
```

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{"code":"NICKNAME_ALREADY_USED","field":"nickname"}
```

오류 한 번에 서버가 확인한 오류 하나만 반환한다. 입력 규칙 위반이 있으면 먼저 `400`으로 응답하고, 유효한 요청에 중복이 있으면 `409`로 응답한다. 같은 단계에서 여러 필드가 동시에 잘못됐을 때 어느 필드가 먼저 반환되는지는 계약에서 보장하지 않는다. 화면은 `code`와 `field`로 해당 입력의 오류를 표시한다.

## 허용·거부 사례

| 사례                                                                    | 기대 결과                           |
| ----------------------------------------------------------------------- | ----------------------------------- |
| 모든 입력 규칙을 만족하고 아이디·닉네임이 새 값                         | `201`                               |
| 허용 문자로 된 새 닉네임이 12자                                         | `201`                               |
| 기존 회원과 성·이름이 같지만 아이디·닉네임은 새 값                      | `201`                               |
| 아이디가 5자 또는 21자, 대문자·공백·기호 포함                           | `400`, `field=loginId`              |
| 닉네임이 1자 또는 13자, 공백 또는 허용되지 않은 기호 포함               | `400`, `field=nickname`             |
| 성 또는 이름이 비었거나 13자, 영문·숫자·공백·한글 자모 포함             | `400`, 해당 필드                    |
| 비밀번호가 7자 또는 33자, 문자 종류 한 가지뿐, 공백·한글·제어 문자 포함 | `400`, `field=password`             |
| 기존 아이디와 정확히 같음                                               | `409`, `code=LOGIN_ID_ALREADY_USED` |
| 기존 닉네임과 같거나 영문 대소문자만 다름                               | `409`, `code=NICKNAME_ALREADY_USED` |

서로 다른 오류가 함께 있는 요청은 위의 단일 오류 응답 규칙을 따른다. 잘못된 JSON 문법과 공통 서버 오류 형식은 이 가입 필드 계약의 범위 밖이다.

## 구현·검증 현황

- 회원가입 `POST`는 구현됐다. 2026-10-07 `check --rerun-tasks`에서 PostgreSQL 통합 테스트를 다시 실행했고, 정상 가입, 아이디·닉네임 중복 거부, 이름 중복 허용과 대표 입력 오류를 다루는 가입 테스트 5개가 실패 없이 완료됐다. 마이그레이션·앱 테스트를 합친 전체 7개도 실패 0건이다.
- 가입 전 중복 확인 `GET`은 공개 조회로 구현됐다. 2026-10-08 `check --rerun-tasks`에서 인증 없는 조회, 새 값과 기존 값, 닉네임 대소문자 중복, 입력 오류와 누락 매개변수의 `code`·`field`를 검증했다. 가입 테스트 14개와 마이그레이션·앱 테스트를 합친 전체 16개가 실패 없이 완료됐다.
- w3 화면은 입력을 약 500ms 멈추면 형식이 맞는 아이디·닉네임을 자동 확인한다. 한글 IME 조합 중에는 조회를 미루고, 입력칸을 떠나면 바로 확인하며, 입력값 변경 시 이전 결과를 지우고 오래된 응답을 무시한다. 최종 가입 요청의 `409`도 표시한다.
- 2026-10-08 로컬 Vite proxy와 Spring 서버를 연결해 가입 `POST 201`, 같은 아이디 재요청 `409`, 가입 전 조회 `200 available=false`를 확인했다. 브라우저에서 중복 아이디 표시를 확인했고, 화면 테스트에서 `201` 완료 안내와 `400`·`409` 필드 오류를 확인했다.

가입 `POST`에서 서비스 사전 조회를 제거하고 DB 충돌을 `409`로 변환한 이유와 검증은 [회원가입 중복 처리 결정](../dev-notes/2026-10-07-member-duplicate-response.md)에 기록했다.
